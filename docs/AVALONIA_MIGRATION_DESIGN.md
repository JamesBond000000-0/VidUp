# VidUp Avalonia移行・GUI近代化設計書

- 作成日: 2026-10-24
- 状態: 設計案（実装未着手・レビュー対象）
- 調査基点: `438f47d` を基点とする作業ブランチの既存コード
- 目的: C#の業務資産と保存データを維持し、Avaloniaによる保守しやすいデスクトップUIへ段階移行する。

> 本書のプロジェクト名・インターフェース名・性能値は、明記した現状以外は提案である。Avaloniaの採用バージョンや各OSでの動作はまだ検証していない。WPFのXAMLをそのまま利用できる前提にはしない。

## 1. 方針と対象範囲

### 1.1 採用方針

1. .NET 10と既存のBusiness / Youtube / Json / Utilsを基本的に維持する。
2. WPF版を残し、新規Avaloniaアプリを並行開発する。既存UIの一括置換はしない。
3. UI内にあるアップロード制御・自動保存・終了処理を、UI非依存のApplication層へ段階的に抽出する。
4. 最初の正式リリースはWindowsの機能互換を優先する。macOS / Linuxは別の検証・出荷ゲートとする。
5. GUIは単なるMaterial Designの再現ではなく、「動画追加→テンプレート確認→公開日時確認→実行」の作業導線を再設計する。
6. 同じデータフォルダーをWPF版とAvalonia版で同時に更新しない。移行中の二重アップロードとデータ破損を防ぐ。

### 1.2 初回リリースの対象

- 動画の追加、ドラッグ＆ドロップ、並べ替え、複数選択、削除。
- アップロード、進捗表示、キャンセル、既存の再開機構、失敗時の再試行。
- テンプレート作成・編集・複製、サムネイル、タグなどの既存属性。
- 公開日時計算、日/週スケジュール、再生リスト、複数YouTubeアカウント。
- カスタムAPI認証情報、ブラウザによるOAuth、設定、診断ログ。
- 自動保存、バックアップ復旧、既存自動化連携、Windowsのスリープ抑止・完了後アクション。
- ライト/ダーク/システム追従、日本語入力、キーボード操作、DPI対応。

初回対象外: Web/モバイル版、Rust化、YouTube APIの全面再実装、動画編集機能、公開スケジュール仕様の変更、全OSの同時正式サポート。自動更新も初回の必須条件には含めない。

## 2. 現状調査と移行上の論点

| 現在の資産 | 確認した構成・依存 | 扱い |
|---|---|---|
| `VidUp.UI` | `net10.0-windows7.0`、WPF + Windows Forms、MaterialDesignThemes 5.4.0 | 新UIを別プロジェクトに作成。TFM名はWindows 7での動作保証を意味しない |
| `VidUp.Business` | `net10.0`、Utils参照 | モデル・スケジュール計算等を継続利用 |
| `VidUp.Youtube` | `net10.0`、Business / Json / Utils参照 | HTTP・認証・アップロード実装を継続利用 |
| `VidUp.Json` | `Content/`、`Settings/`、`Automation/`、`AtomicFileWriter` | 保存形式と原子的書き込みを維持 |
| `VidUp.Utils` | `Settings.Instance`、UserSettings、ログなど | 既存互換を保ちつつ境界から依存を注入 |
| `VidUp.Test` | `net10.0-windows`、UIを参照 | UI非依存テストを別プロジェクトへ分離 |
| `VidUp.Setup` / release workflow | Windows向け既存配布経路 | WPF経路を維持し、新UIの成果物と明確に分離 |

### 2.1 「ViewModelをそのままコピー」できない箇所

- `MainWindowViewModel`: WPF Dispatcher、タスクバー、アプリ終了、データ復旧ダイアログ。
- `UploadRibbonViewModel`: アップロード制御、Windows電源制御、UIスレッド処理。
- `UploadViewModel` / `TemplateViewModel`: Windows Formsダイアログ、WPF画像型など。
- `ObservableUploadViewModels`: WPF Controlsへの依存。
- `DisplaySchedule*ViewModel` / `CultureViewModel`: WPFの色・描画型。
- `Controls/*.xaml`: WPF / MaterialDesign固有スタイル、トリガー、DialogHost等。
- `MainWindow.xaml.cs`: ファイルドロップ、終了時の保存待ち。

これらは「業務ロジック」「画面状態」「OS/UI操作」に分離する。下位ライブラリが `net10.0` であることだけでは、OS非依存の動作保証にならないため、パス・プロセス・ファイル監視も監査する。

各ライブラリに `VidUp.UI/AssemblyInfo/CommonAssemblyInfo.cs` のリンク参照もある。新構成では共通メタデータをUI外の共有ファイルまたは共通ビルド設定へ移し、ビルド時の逆向きファイル依存も解消する。

## 3. 目標アーキテクチャ

```text
VidUp.Desktop (新規: Avalonia / Views / UIアダプター / 起動構成)
    ├── VidUp.Presentation (新規: UI型を含まないViewModel・画面状態)
    │       └── VidUp.Application (新規: ユースケース・サービス境界)
    ├── VidUp.Platform (新規: Windows等のOSアダプター)
    └── 既存ライブラリ・各実装を起動時に組み立てる

VidUp.Application → VidUp.Youtube / VidUp.Json / VidUp.Business / VidUp.Utils
既存: Youtube → Business / Json / Utils、Business → Utils を当面維持
VidUp.Platform → Applicationのインターフェース（OS実装の注入）
VidUp.UI (既存WPF) → 段階的にApplication層を利用
```

新規3層は責務の境界であり、細分化自体を目的にしない。移行時に下位層からDesktop / WPF / Avaloniaへ参照を追加しない。OS固有APIが必要なPlatformはマルチターゲットまたはOS別実装に分割し、共通契約をWindows専用TFMにしない。

### 3.1 責務

- **Application**: アップロードキューの実行・停止・再試行、テンプレート適用、公開日時再計算、保存・復旧、終了手順。既存UploaderやJSON実装を包み、最初から書き直さない。
- **Presentation**: Shell / UploadQueue / UploadDetails / Templates / Schedule / Playlists / Accounts / SettingsのViewModel。UI固有のColor / Bitmap / Windowを持たず、状態・文字列・画像パス等を公開する。
- **Desktop**: AvaloniaのView、画像読み込み、UIスレッド・ダイアログ実装、Fluentテーマ、DI構成。
- **Platform**: 電源、外部ブラウザ、ファイル表示、タスクバー等。利用可否を能力情報として返す。

### 3.2 主な境界（名称は仮）

| 境界 | 役割・契約 |
|---|---|
| `IUploadCoordinator` | 既存Uploaderを利用した開始・停止・再試行、状態スナップショットと進捗通知 |
| `IRepositoryStore` | JSONの読込・保存・バックアップ復旧、単一書き込み経路 |
| `IUiDispatcher` | UIへの通知を非同期で配送。WPF / Avalonia / テスト用に実装 |
| `IUserInteraction` | 確認・エラー通知・ファイル選択。キャンセルと所有ウィンドウを扱う |
| `IPowerService` | スリープ抑止の取得/解放、対応する完了後アクションの列挙 |
| `IDesktopIntegration` | ブラウザ起動、フォルダー表示、任意のOS進捗表示 |
| `ICredentialStore` | トークン等の保存・削除。OS保護の可否と移行を扱う |
| `IAppLifetime` | 未保存・転送中状態を確認した非同期終了 |
| `IStorageLocationProvider` | データ/画像/ログの場所、移行元、テスト用ディレクトリの注入 |

初期段階から全クラスをDI化しない。`Settings.Instance` と既存EventAggregatorは互換アダプターを介して残し、新規画面のグローバル依存を増やさない。イベント購読は破棄時に解除する。

### 3.3 非同期・状態管理

- アップロードエンジンはウィンドウから独立して生存。画面遷移で転送を止めない。
- コマンドは非同期化し、実行中の多重押下を禁止。`async void`はUIイベント境界以外に増やさない。
- 待機/検証中/転送中/停止処理中/失敗/完了をUI状態へ明示的に写像する。キャンセルを成功と表示しない。
- 既存の転送状態とYouTube側の処理・公開状態を区別する。新しい表示状態を既存JSONの列挙値へ無断追加しない。
- 進捗通知はUIで最大毎秒5回程度に集約し、最終状態・エラーは取りこぼさない。全行を毎回再描画しない。
- 終了は「新規受付停止→キャンセル/終了待ち→再開情報と状態保存→電源抑止解放→終了」。タイムアウト時は未保存の可能性を明示し、既存の保存待ちの保証を退行させない。

## 4. GUI近代化

### 4.1 情報設計

常設サイドナビゲーションを採用し、主要作業を隠れたドロワーやアイコンだけに依存させない。

- アップロード（初期画面）
- テンプレート
- 公開スケジュール
- 再生リスト
- アカウント
- 設定 / ヘルプ・バージョン情報

アカウント選択は共通ヘッダーに置き、現在の操作対象とキュー各行の送信先を明示する。フィルターの変更で既存キューの送信先を変更しない。

### 4.2 アップロード画面ワイヤーフレーム

```text
┌──────────────────────────────────────────────────────────────────────┐
│ VidUp                 対象アカウント [▼]              通知 / 接続状態 │
├────────────┬─────────────────────────────────────────────────────────┤
│ アップロード│ アップロード    [動画を追加]             [開始 / 停止] │
│ テンプレート│ [検索…] [状態▼] [テンプレート▼]                        │
│ スケジュール├───────────────────────────────────┬─────────────────────┤
│ 再生リスト  │ □ 動画 / 送信先 / 公開日時 / 状態  │ 選択動画の詳細      │
│ アカウント  │ □ サムネイル タイトル   進捗       │ テンプレート [▼]    │
│             │ □ サムネイル タイトル   待機       │ タイトル・説明・タグ│
│             │                                   │ サムネイル・再生リスト│
│ 設定        │ ドロップで動画追加                 │ 公開日時 / 検証結果 │
├────────────┴───────────────────────────────────┴─────────────────────┤
│ 全体進捗 / 件数 / 転送量 / 速度 / 残り目安    完了後: [何もしない▼] │
└──────────────────────────────────────────────────────────────────────┘
```

- リストは仮想化する。主要列は動画名、アカウント、テンプレート、公開日時、状態、進捗。列幅・表示列は調整可能にする。
- 右ペインでメタデータを編集し、モーダルの連続を避ける。転送中の編集禁止は理由付きで表示する。
- 複数選択では共通値と混在値を区別し、一括変更前に件数と影響を提示する。
- 狭いウィンドウでは詳細ペインを別画面へ切替。主要操作のボタンが隠れないようにする。
- 並べ替えはドラッグに加えキーボード操作も提供する。ソート表示と実行順の変更は別の操作にする。
- 初期状態には「動画を追加」と対応形式の説明。失敗行には短い原因、再試行、詳細ログを表示する。
- 大量追加時は非同期で検証し、重複・ファイル不在・テンプレート未一致を結果一覧で知らせる。

### 4.3 画面ごとの改善

| 画面 | 設計 |
|---|---|
| テンプレート | 左に検索可能な一覧、右に基本/メタデータ/公開ルール/高度な設定。変数を使った結果を実動画名でプレビュー。未保存状態と適用対象を表示 |
| スケジュール | 日/週切替と一覧表示。タイムゾーンと絶対日時を表示し、再計算前に変更前後の差分・対象件数を確認。YouTubeの予約公開とローカル転送を区別 |
| 再生リスト | アカウントで絞り込み、同期中・取得失敗・削除済みを区別。破壊的操作は対象を明記 |
| アカウント | 接続状態、再認証、解除を集約。ログアウトとローカルデータ削除を別操作にする |
| 設定 | 一般/アップロード/自動化/認証/診断に分類。ネットワークの高度な値は通常操作から分離 |
| 復旧・通知 | バックアップ復旧は永続バナーで対象ファイルと注意点を表示。一時的な成功は軽い通知、操作不能な問題のみダイアログ |

### 4.4 デザインシステム

- Avalonia標準Fluentテーマを起点に、少数の独自リソースで統一。追加の大規模UIテーマはPoC後に必要性を判断する。
- 色・余白・角丸・文字サイズをトークン化。余白は4/8/12/16/24、角丸は4/8を基本とする。
- アクセントは青系、成功/注意/失敗は文字・アイコンも併用。色だけで状態を伝えない。
- 本文14 DIP程度を起点とし、OSフォントフォールバックで日本語を欠損させない。固定行高による文字切れを避ける。
- ライト/ダーク/システム追従、明確なフォーカス枠、標準のウィンドウ操作を優先する。過度な透過・独自タイトルバー・装飾アニメーションは初回対象外。
- Googleサインインはブランドガイドラインに沿った表示を維持し、テーマ変更でロゴを不適切に加工しない。

### 4.5 アクセシビリティ・日本語

- Tab順、ラベル、スクリーンリーダー用名称、エラーの読み上げ対象を定義する。Windows実機で確認する。
- Ctrl+O: 動画追加、Ctrl+F: 一覧検索。Deleteは編集入力中にキュー削除として扱わない。開始/停止など重大操作は誤爆しない導線にする。
- 100/150/200% DPI、キーボードのみ、長い日本語タイトル、IME変換、複数モニターを検証する。
- UI文言はリソースへ分離し、日本語と英語を初回対象とする。保存済みの動画タイトル等は翻訳しない。
- 1280×720・100%を初期の最小レイアウト検証条件とする。高DPIで領域不足の場合はスクロールと詳細画面への切替で操作を維持する。

## 5. データ互換・認証・安全性

### 5.1 データ

現状の保存先は `Settings` により `MyDocuments/VidUp{suffix}/{subFolder}` に組み立てられる。`TemplateImages`、`FallbackThumbnailImages`、`settings.json`、アカウント/テンプレート/アップロード/再生リスト等のJSONを移行対象として棚卸しする。ファイル名・参照関係は既存シリアライザーを正とする。

1. PoC/プレビューは必ず専用コピーを利用。元データを自動で書き換えない。
2. 正式移行時は旧アプリ終了を確認し、データ・画像を時刻付きバックアップへ複製する。
3. JSONを既存デシリアライザーで読み、ID・参照・ファイル数・再開情報を検証。不正データの復旧は既存仕様を維持する。
4. 最初の保存で暗黙の形式変更をしない。UI専用設定（テーマ、列幅等）は別の版管理されたファイルへ保存し、旧版との往復を妨げない。
5. 原子的保存・バックアップ・排他制御を維持する。新旧アプリが同じ領域を開く場合、両方に効くプロファイルロックを導入する。ロック未対応の旧配布版には同時起動禁止を明示し、安全を保証できない場合はインポートコピー方式のみ許可する。
6. ロールバックは新UIを終了後、バックアップを別領域へ復元してWPF版を起動。移行後にアップロード済みの動画を照合し、自動再送しない。

別OSへの移動ではWindows絶対パスをそのまま使用できない。動画・画像の再リンク画面を用意し、大文字小文字・権限・無効文字を検証する。公開日時の既存保存仕様を確認し、タイムゾーン変更で意図せず再計算しない。夏時間境界も回帰テストに含める。

### 5.2 OAuthと資格情報

- 既存の外部ブラウザ＋ループバックリダイレクト＋PKCEを維持。埋め込みWebView認証に置き換えない。
- キャンセル、ポート競合、コールバック待ちタイムアウト、ブラウザ起動失敗、トークン更新失敗をテストする。既存のstate/PKCE検証を退行させない。
- 現在のトークン・カスタムclient ID/secretの保存箇所を監査し、OS保護ストア移行は別の明示的な手順にする。利用できない環境で平文保存へ黙ってフォールバックしない。
- ログと診断エクスポートからトークン、Authorizationヘッダー、client secret、再開セッションURI等を除去する。
- 認証情報や未マスクの実データをテスト資産・Git・CI成果物へ含めない。

## 6. OS対応・依存関係・配布

### 6.1 対応段階

| 機能 | Windows初回 | macOS / Linuxプレビュー |
|---|---|---|
| UI・ファイル操作・OAuth・アップロード | 必須 | 必須の検証対象 |
| スリープ抑止 | 既存動作を維持、失敗時も必ず解放 | OS別APIを検証、未対応時は警告 |
| シャットダウン/サスペンド等 | 既存設定を明示確認し維持 | 権限・デスクトップ環境に依存。未対応操作は非表示または理由付き無効 |
| タスクバー進捗 | 可能な範囲で既存互換 | 任意。アプリ内表示は常に提供 |
| 署名・インストーラー | 正式版の必須条件 | 各OSの正式出荷前に別途対応 |

初回の正式サポートはWindows 11 x64を基準案とし、Windows 10・ARM64・x86は利用状況と採用ランタイムのサポートを確認後に決定する。macOS / Linuxの最低OS版・ディストリビューション・CPUもPoC後に固定し、「Avalonia対応＝VidUp対応」と表記しない。

### 6.2 ライブラリと配布

- Avalonia / Desktop / Fluent / 必要なDataGridは、.NET 10との互換性をPoCで確認した同じ安定系列に固定する。現時点で未確認の最新版番号を設計上の前提にしない。
- MVVM支援はCommunityToolkit.Mvvmを候補とする。既存GenericCommandは直ちに全置換せず、非同期コマンドが必要な箇所から移す。
- Avaloniaの型付き/コンパイル済みBindingを原則とし、DataContextの型を明示する。
- 既存WPFインストーラーと別名・別出力にし、同じ起動ファイルへ上書きしない。`release-installer.yml` は新UIの検証が終わるまで維持する。
- Windowsはまずx64 self-containedを候補としてクリーン環境で比較する。サイズ・初回起動・ランタイム依存を測り配布方式を確定する。単一ファイル化やトリミングは互換性確認後とする。
- macOSの署名/公証、Linuxパッケージ方式、外部依存・ライセンス表示はそれぞれ出荷ゲートにする。コード署名鍵はCIのシークレット管理を使用する。

## 7. 段階的実装計画

| 段階 | 主な作業・成果物 | 完了ゲート |
|---|---|---|
| P0: 棚卸し | 現行機能/コマンド/保存ファイル/自動化の対応表、Windowsで現行テスト実行、画面・性能基準値、採用パッケージ検証 | 未対応項目とテスト結果が可視化され、対象OSと初回範囲を合意 |
| P1: 技術PoC | 新DesktopのShell、Fluentテーマ、日本語入力、仮想化リスト、ファイル選択/D&D、コピーしたデータの読み取り | Windowsで起動・DPI・IME・1,000行表示を検証。データ更新や実アップロードをしない |
| P2: 基盤抽出 | Applicationとサービス境界、UI非依存テスト分離、保存/終了/電源制御の抽出 | WPFの挙動が維持され、共通コードからUIアセンブリ参照が除去される |
| P3: 縦方向の一通り | 認証→動画追加→テンプレート→予約日時確認→アップロード→保存/再開 | 専用アカウント・小さい非公開動画で実API動作を確認。二重実行なし |
| P4: 全画面・近代化 | 一括操作、テンプレート編集、日/週表示、再生リスト、設定、通知、アクセシビリティ | 機能対応表の初回必須項目がすべて受入済み |
| P5: 移行・配布 | バックアップ/排他/復元、署名、インストーラー、障害試験、利用手順 | クリーンWindowsで導入・移行・アンインストール・旧版復帰を確認 |
| P6: 他OS | OSアダプター、パス再リンク、権限、署名/パッケージ、実機試験 | OS別チェックリストを通過した組合せのみサポートを宣言 |

各段階は小さいPRに分け、業務ロジック変更と画面デザイン変更を可能な限り分離する。工数・日程はP0/P1後に見積もる。既存WPFの削除は新UIの安定運用・復旧手順の検証後に別判断とする。

### 最初の実装PR（推奨）

- `VidUp.Desktop` の追加とShellのワイヤーフレーム実装。
- ダミー/読取専用キュー、テーマ切替、日本語リソース、仮想化リスト。
- ファイル選択とD&DのPoC。コピーしたプロファイル以外へアクセスしない安全策。
- Windows CIのビルドと、PoCの手動確認手順。
- この段階ではWPF、保存形式、認証、アップロードの既存実装を変更しない。

## 8. テスト・受入基準

### 8.1 テスト構成

- `VidUp.Core.Tests`（新規、`net10.0`）: UI非依存の既存テストを移し、スケジュール、JSON互換、HTTP応答解析、再開位置、ファイル処理、状態遷移を検証。
- 既存 `VidUp.Test`: WPF特有の回帰をWindowsで継続実行。過去の件数ではなく移行開始時の結果を基準とする。
- `VidUp.Desktop.Tests`（新規）: ViewModelとサービス代替実装、AvaloniaのヘッドレステストでBindingと画面遷移を検証。
- ヘッドレスでは保証できないIME、実DPI、D&D、スクリーンリーダー、OSダイアログ、電源操作は実機試験。
- CIはWindows/Linuxで共通テスト、WindowsでWPF/新UIビルド。macOSは対象段階で追加する。実APIテストは通常PRで自動送信せず、承認付きの専用環境で行う。

### 8.2 必須シナリオ

1. 旧データのインポート・保存・再読込でID、テンプレート、画像、公開日時、キュー順を維持。
2. 壊れたJSON、バックアップ復旧、書き込み権限なし、ディスク不足、保存中強制終了からの復旧。
3. 認証取消、期限切れ、API割当超過、通信断、再開セッション失効、キャンセル、再試行。
4. 転送中のアカウント切替・編集・終了で対象を混同せず、二重アップロードしない。
5. 公開日時再計算、日付境界、夏時間、時差、再生リスト自動追加、既存自動化出力の回帰。
6. ドロップ/ファイル選択、複数選択、重複追加、欠損サムネイル、長いパス、非ASCIIパス。
7. スリープ抑止の正常/例外/取消時の解放。完了後アクションは全キューの状態とユーザー設定を確認し、失敗時に危険な操作へ進まない。
8. マルチモニターから単一モニターへ変わってもウィンドウが画面外へ消えない。
9. 新旧アプリの同時起動、インポート中断、バックアップからの復帰、移行後の重複送信防止。

### 8.3 GUI・性能の暫定目標

以下は測定前の目標であり、達成済みの数値ではない。P0で同一Windows端末・Release構成・同一データセットを記録し、P1で確定する。

- 1,000件のキューで仮想化が機能し、検索/選択の反応が概ね200ms以内。
- 起動のコールド/ウォームを各5回測定し、中央値・最大値・操作可能になるまでの時間を報告。
- 1,000件表示と転送中のメモリをWPF版と比較。無制限な画像キャッシュや購読リークがなく、画面切替・長時間運転で継続増加しない。
- 通信待ち・保存待ちがUIスレッドをブロックしない。開始/停止のフィードバックを即時表示。
- ライト/ダーク、DPI、IME、キーボード、画面読み上げの必須ケースに重大な操作不能がない。

## 9. 主なリスクと対策

| リスク | 対策 |
|---|---|
| UIに隠れた業務処理の取りこぼし | ViewModel/Command/イベントと新ユースケースの対応表、WPF共存回帰 |
| XAMLやテーマ差異による工数増 | P1で代表的な一覧/編集/ダイアログを先に検証、WPFスタイルを機械移植しない |
| 保存/再開情報の破壊 | 形式維持、専用コピー、原子的保存、往復テスト、復元訓練 |
| イベントの二重購読・UIスレッド違反 | 購読の寿命管理、Dispatcher境界、連続遷移テスト |
| 他OS対応による初回遅延 | Windows正式版と他OSゲートを分離、未対応機能を能力情報で表示 |
| UI刷新で既存ユーザーが迷う | 主要用語を維持、機能対応表、初回導線、実作業でのレビュー |
| 署名・配布環境でのみ発生する不具合 | self-contained等の選定を測定し、クリーンOS・実配布物で検証 |
